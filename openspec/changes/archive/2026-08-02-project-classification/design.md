## Context

The story graph currently seeds `Change {name}` → `HAS_STORY` → `Story {id, change}` with `DEPENDS_ON` edges between stories, generated by `scripts/story_driver.clj generate` into `story-seed.cypher` and executed via the Neo4j MCP Cypher tool. All lifecycle queries in `skills/openspec-story-driver/SKILL.md` match nodes by `{name}` / `{id, change}` only. There is no project dimension: same-named changes in different repositories collide, and no classification metadata exists.

The frozen proposal (`proposal.md`) commits to: `Project` nodes with classification (`name` = canonical repo identity, `repoUrl`, `techStack`, `type`), `BELONGS_TO` edges, project-scoped `Change {name, project}` and `Story {id, change, project}` identity, project filtering on every story-graph query (polling, readiness, transitions, blocked/completion, seeding/resume guard, selection), a required `--project` flag on `generate`, a registration/classification flow written via the MCP Cypher tool, and BREAKING updates to seed output, the CLI contract, and harness-adapters parity. Legacy unowned nodes are excluded, with no migration.

## Goals / Non-Goals

**Goals:**
- Deterministic project identity from the repository, stable while `origin` is unchanged.
- Full project isolation: same change/story names in different projects share no state.
- Classification (repoUrl, techStack, type) written by the agent via MCP, refreshed on re-run.
- Every generated seed links its change to the owning project (required `--project`).
- All story-graph queries in the skill become project-scoped.

**Non-Goals:**
- No migration/backfill of legacy unowned nodes.
- No change to story lifecycle semantics (statuses, task sync, compaction, confirmation).
- No changes to decomposition or install capabilities.
- No new dependencies or new write paths (MCP Cypher tool only).

## Decisions

### D1: Project name derivation (canonical + fallback)

Project name = git remote `origin` URL normalized to `host/owner/repo` (lowercase, no `.git` suffix, no protocol/port/trailing slash), e.g. `https://github.com/aplacaba/agent-skills.git` → `github.com/aplacaba/agent-skills`. The parsing boundary is exact:

- Parse the URL with a git-remote-aware parser. Accept HTTPS (`https://host/owner/repo[.git]`), SSH scp-style (`git@host:owner/repo[.git]`), and SSH URL forms (`ssh://[user@]host[:port]/owner/repo[.git]`).
- Strip: scheme prefix, userinfo (`user@`, including `git@`), port, `.git` suffix, trailing slashes, query strings, and fragments.
- Identity path = `host/<all path segments except the last>/<last path segment>` — i.e. the owner part is all-but-last segments joined with `/`, preserving GitLab subgroups (`host/owner/group/repo` → `host/owner/group/repo`).
- Lowercase the entire result (host, owner, subgroup segments, and repo name).
- `repoUrl` (the classification property) is a separate, sanitized value (see D4); it is NOT the identity.

An origin is **unparseable** when: the URL has no host, no path, fewer than two path segments, or the scheme/userinfo/path cannot be matched by the forms above. On unparseable or absent origin: fallback `local/<basename-of-repo-directory>`, e.g. `local/my-agent-skill`; the basename is lowercased as well, so the fallback follows the same lowercase rule as origin-derived names.

*Alternatives considered:* owner/repo only (rejected: host collisions); arbitrary human-chosen names (rejected: not deterministic); UUID per clone (rejected: not stable across clones). Trade-off documented in proposal: `local/<dir>` is best-effort (two unrelated local repos with the same dir name share a project until `origin` is set); adding/removing `origin` starts a new project identity with no migration.

### D2: Project-scoped graph model

- `MERGE (p:Project {name: <project>})` — identity key is `name` only.
- `MERGE (c:Change {name: <change>, project: <project>})` — identity is the pair.
- `MERGE (s:Story {id: <storyId>, change: <change>, project: <project>})` — identity is the triple.
- Edges: `(p)-[:BELONGS_TO]->(c)`, `(c)-[:HAS_STORY]->(s)`, `(a)-[:DEPENDS_ON]->(b)` — all endpoint MATCHes include the `project` property (change and story carry it, so MATCH filters use `{id, change, project}` / `{name, project}`).

Rationale: adding `project` to identity keys is the minimal change that guarantees isolation without composite key workarounds; Neo4j MERGE on multi-property maps is native.

*Alternatives considered:* scoping via `BELONGS_TO` traversal only (rejected: `Story` nodes would still collide on `{id, change}` when matched directly; lifecycle queries match stories directly). Separate databases per project (rejected: new dependency/ops complexity, breaks single-graph queries across projects).

### D3: Seed generation (`generate --project`)

`generate` gains a required flag `--project <name>` (parsed with `--root`/`--def` style). When missing → argparse-style error: usage + `the following arguments are required: --project` on stderr, exit 2 (preserved CLI contract); when `--project` is the last token with no value, or the next token is another flag, → `argument --project: expected one argument`, exit 2. Seed layout per project:

```cypher
MERGE (p:Project {name: "..."});
MERGE (c:Change {name: "...", project: "..."});
MATCH (p:Project {name: "..."}), (c:Change {name: "...", project: "..."})
MERGE (p)-[:BELONGS_TO]->(c);
MERGE (s:Story {id: "...", change: "...", project: "..."})
ON CREATE SET s.title = ..., s.description = ..., s.acceptanceCriteria = ..., s.taskRefs = ..., s.status = "pending";
MATCH (c:Change {name: "...", project: "..."}), (s:Story {id: "...", change: "...", project: "..."})
MERGE (c)-[:HAS_STORY]->(s);
// DEPENDS_ON edges with three-property MATCHes
```

The ownership statement is emitted literally as two statements:

```cypher
MERGE (p:Project {name: "..."});
MATCH (p:Project {name: "..."}), (c:Change {name: "...", project: "..."})
MERGE (p)-[:BELONGS_TO]->(c);
```

Header comment gains the project line. Stories merge with `ON CREATE SET` exactly as today (identity change only).

### D4: Classification/registration flow (agent-driven via MCP)

The skill documents: an agent derives facts from the repository (README first paragraph for `type`; manifest files — `package.json`, `deps.edn`, `Cargo.toml`, `pyproject.toml` — and directory layout for `techStack`; `git remote get-url origin` for `repoUrl`) and writes:

```cypher
MERGE (p:Project {name: "<project>"})
SET p.repoUrl = "<url>", p.techStack = ["clojure", "js"], p.type = "tooling";
```

`SET` (not `ON CREATE SET`) so re-running refreshes classification. Stale-property semantics: classification is a full overwrite of the three derived properties (`repoUrl`, `techStack`, `type`) on every run — the agent SHALL `SET p.repoUrl = <value>, p.techStack = <list>, p.type = <value-or-null>` where a value that is no longer derivable is written as `null` (Neo4j removes the property on `SET ... = null`), so reclassification cannot leave stale values behind.

**repoUrl sanitization**: the stored `repoUrl` MUST NOT contain credentials — strip userinfo (usernames, access tokens, passwords), query strings, and fragments from the origin before storing. The retained representation is the full normalized URL path after stripping those parts: for HTTPS keep `https://host/owner/repo` (with any `.git` suffix retained as in the origin); for scp-style/SSH origins, convert to the equivalent HTTPS form `https://host/owner/repo` when the host is a known forge (github.com, gitlab.com, bitbucket.org), otherwise omit `repoUrl` entirely. If the origin has no safe URL form, omit `repoUrl`.

Vocabulary contract: `type` ∈ `{tooling, agent, docs}` (unknown → write `null` rather than invent); `techStack` is a lowercase list of concrete runtime/language names from manifests/dirs, canonicalized by deduplication, sorted deterministically (alphabetical), with alias normalization (`js`/`javascript` → `javascript`, `ts`/`typescript` → `typescript`, `py` → `python`); runtimes and languages are both recorded when present (e.g. `["node", "typescript"]`). The `name` used must be derived via D1. The flow is documented, not scripted — no new subcommand, no file format.

*Alternatives considered:* new `classify-project` subcommand (rejected: classification is context-dependent judgment, better done by the agent; a script cannot read "README intent"); static `projects.yaml` seed file (rejected: agent-derived per user's choice, and a file would drift from the repo).

### D5: Project-scoped queries in the skill

Every Cypher snippet in `skills/openspec-story-driver/SKILL.md` that matches `Change`/`Story` gains the project property:

- seeding/resume guard: `MATCH (c:Change {name: "<name>", project: "<project>"})-[:HAS_STORY]->(s:Story {project: "<project>"}) ...` (run-in-progress check).
- next-runnable poll: project-scoped MATCH + `DEPENDS_ON` targets matched within the same project.
- status transitions: `MATCH (s:Story {id: "<story-id>", change: "<name>", project: "<project>"}) SET s.status = ...`.
- blocked/completion checks and the graph-schema reference section: project-filtered.

*Alternatives considered:* leaving the skill's queries unchanged and relying on unique change names (rejected: proposal requires project isolation). Parameterizing via a `:project` query parameter everywhere (rejected: snippets are inlined docs; literal property filters are clearer for agents copying them).

## Risks / Trade-offs

- [Local fallback collision (two local repos, same dir name)] → documented trade-off; agents instructed to set `origin`; identity changes to `host/owner/repo` once origin is added (no migration — BREAKING, per proposal).
- [Existing graph data becomes invisible to scoped queries] → BREAKING, documented in proposal; legacy nodes remain untouched in the DB, excluded from queries; re-seeding a change creates fresh project-scoped nodes.
- [Classification vocabulary drift between agents] → D4 defines the `type` vocabulary and `techStack` normalization contract; tests cover seed shape, not agent judgment.
- [Golden fixtures churn] → goldens are captured once from the new `generate` output and become the parity baseline (harness-adapters updated).
- [Stories in different projects with same id/change no longer collide] → intended; DEPENDS_ON matching is fully scoped via the triple.
