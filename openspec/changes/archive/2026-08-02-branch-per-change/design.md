## Context

This repository currently commits every change directly to `master`, so propose/implement/sync/archive commits from different changes interleave on one branch and there is no per-change review or rollback point. The `openspec-propose`, `openspec-apply-change`, `openspec-sync-specs`, and `openspec-archive-change` skills currently perform no git operations at all — they leave committing entirely to the user. This design introduces a worktree-per-change git workflow: each change gets a dedicated git worktree under `.worktrees/<name>/` on branch `change/<name>`, the main checkout stays on the default branch and is never switched, and the archive step ends with a deterministic post-archive handoff — commit remaining work, push the change branch, open a pull request against the default branch, and remove the worktree. Merging is deliberately left to the pull request's review process (the user's decision), and the branch (local and remote) is kept until the pull request merges. This is the model decided in the proposal: worktree per OpenSpec change, push-branch-and-create-PR as the archive post-ops, no Neo4j story-graph cleanup.

The repo facts that constrain the design: default branch is `master`; canonical skills must stay harness-neutral (generic wording, no tool-specific tokens — pull-request creation is described via the forge's generic pull-request tool, mapped per `docs/harness-mapping.md`); `AGENTS.md` binds agent conventions and its derived-fact lines must be updated with the docs; bug fixes need no proposal and stay exempt.

## Goals / Non-Goals

**Goals:**
- One git worktree `.worktrees/<name>/` on branch `change/<name>` per OpenSpec change, created at propose time, carrying all work of the change, pushed to the remote with a pull request opened against the default branch at archive time, then removed.
- The main checkout is never switched; it stays on the default branch for the whole change lifecycle.
- Deterministic, fail-safe post-archive git steps: commit remaining work, push the change branch, open the pull request, remove the worktree, report the pull request URL.
- Enforcement across the whole workflow: propose creates the worktree, apply and sync operate inside it, archive performs the push-and-pull-request handoff and worktree removal.
- The strategy is documented in `README.md`/`AGENTS.md` so both humans and agents follow it.
- Skills behave safely outside this repository's convention (no git repo, no remote, no pull-request-capable forge, standalone store): warn or no-op instead of failing or doing damage.

**Non-Goals:**
- Merging the change into the default branch (done by the user through the pull request, not by the archive flow).
- Branch per story in the story-driven workflow (stories run inside the change worktree).
- Publishing change branches to the remote before archive time.
- Deleting the change branch (local or remote) at archive time; the branch is kept until the pull request merges. Only the worktree is removed.
- Git hooks, CI, or any enforced git policy beyond the documented convention and skill behavior.
- Changing the default branch name or rewriting history.
- Any cleanup of the Neo4j story graph.

## Decisions

### D1: Worktree and branch lifecycle

Each proposed change gets a git worktree at `.worktrees/<name>/` checked out on branch `change/<name>` (where `<name>` is the kebab-case change name). The worktree and branch are created at propose time. All change work happens inside the worktree; the main checkout stays on the default branch and is never switched. At archive time the branch is pushed to the remote, a pull request `change/<name>` → default branch is opened, and the worktree is removed (safe because the branch is already pushed); the branch (local and remote) is kept until the pull request merges, after which it may be deleted by the user or the forge. The default branch receives proposed-change commits only when a pull request merges; bug fixes (no proposal) commit directly on the default branch in the main checkout as today.

Rationale: worktrees give true isolation — no branch switching, no dirty-tree cross-contamination between changes, no interaction with the main checkout's state; the strict lifecycle ties git state to OpenSpec state so the archive step always ends with a reviewable handoff. Alternative rejected: switching a single checkout between branches — every earlier design-round issue about dirty trees, switch guards, and cross-contamination disappears with worktrees.

### D2: Convention detection (repo-local guard)

A repository uses this convention when BOTH hold:

1. It is a git repository (`git rev-parse` succeeds), and
2. Its root `AGENTS.md` contains the exact heading `## Branching strategy` with the documented `change/<name>` worktree convention (the heading is the stable marker; a repo adopts the convention by adopting that section).

Each skill evaluates this before any git operation. When the convention is inactive: the skill warns once and skips all git steps (no worktree creation, no verification, no handoff). The archive still completes; only the git post-ops are skipped. A missing change worktree in a convention-active repository is a workflow violation that stops apply/sync/archive — it is never treated as evidence that the convention is inactive.

Rationale: this gives every skill a single, documentable, harness-neutral detection rule and keeps the canonical skills safe in foreign repositories and standalone OpenSpec stores. Alternative rejected: inferring the convention from the presence of `openspec/` — a store may have specs without adopting this git workflow.

### D3: Shared ensure-worktree procedure

All skills that need to work on a change use one shared procedure, "ensure the change worktree at `.worktrees/<name>/`":

1. If not a git repository or convention inactive (D2): warn, skip.
2. If the worktree exists: verify it is a registered git worktree on exactly branch `change/<name>` — check `git worktree list --porcelain` for the path `.worktrees/<name>/` and its branch — and only then operate there (all change operations — artifact writes, commits, story work — run with the worktree as the working directory). A stale directory at that path, or a worktree on another branch, is a violation: stop and report.
3. If the worktree does not exist and this is the **propose** phase (the designated creation point): verify the main checkout is on the resolved default branch (D5) — if not, stop and ask the user (an already-switched main checkout silently violates the documented invariant); then create the worktree with `git worktree add -b change/<name> <path> <start>` from the main checkout; if branch `change/<name>` already exists (re-propose/resume), `git worktree add <path> change/<name>` instead. `<start>` is explicitly tied to the selected remote (D5): run `git fetch <remote> <base>` and use `FETCH_HEAD` as the start point — it is the tip of that branch at fetch time, guaranteed current, and never depends on a local tracking ref or local branch existing (`git ls-remote --symref` does not update remote-tracking refs; a fetch failure stops and reports). With no remote, the base is the first existing local branch of `master`/`main`, else stop and ask the user. The main checkout is never switched.
4. If the worktree does not exist in **apply/sync/archive** phases and the convention is active (D2): STOP and report — a proposed change without its worktree is a broken state; do not create it late (the branch may lack the change's commits) and do not fall back to the main checkout; suggest re-running the propose phase or creating the worktree manually. In foreign repos (convention inactive) the step-1 guard already warns and skips.
5. Bug fixes: skip — they commit directly on the default branch in the main checkout.

In this repository the invariant "proposed work only inside its change worktree" is enforced by stopping/asking; in foreign repos step 1's guard applies. Because worktrees are independent checkouts, no dirty-tree rules for branch switching are needed — the main checkout's state never affects change work.

### D4: Enforcement points

- **Propose**: run the shared preflight (D6.0) and ensure-worktree (D3) first — this creates `.worktrees/<name>/` with branch `change/<name>` from the default branch; the main checkout stays untouched. Then run `openspec new change "<name>"` and write the artifacts inside the worktree. When all artifacts are done and verified, run the shared preflight again immediately before staging/committing, then commit with `chore(openspec): propose change <name>`, staging **only** files under `openspec/changes/<name>/` (relative to the worktree).
- **Apply**: before starting, run the shared preflight (D6.0) and ensure-worktree (D3), then operate inside the worktree. No blanket commit policy — the agent commits per the repo's conventional-commit rules as it works, and the shared preflight SHALL run immediately before every such commit.
- **Sync**: before syncing, run the shared preflight (D6.0) and ensure-worktree (D3), then operate inside the worktree; after the sync, run the shared preflight again immediately before the commit of the delta spec changes with `chore(openspec): sync <name> specs`.
- **Archive**: before the archive move (before `mv` of the change directory inside the worktree), run the shared preflight (D6.0) and ensure-worktree (D3) so the invariant holds before any file moves; then sync, then perform the post-ops handoff (D6). The archive skill records the exact archive destination and the complete D5 pin set — remote name, effective push endpoint list, base repository identity (normalized fetch endpoint), and resolved base branch — before the move, and its completion/failure report names the resume command, which carries the destination AND all pins — not just the change name. The resume dispatch (when invoked with an already-moved archive destination) SKIPS the pre-move ensure-worktree check and enters D6 directly: after a successful move the worktree may legitimately be gone, and the post-ops state locator decides what remains to do.
- **`.gitignore`**: this change adds `.worktrees/` to `.gitignore` so change worktrees are never tracked.

### D5: Remote and default-branch selection

Every remote-touching step (default-branch detection, push, remote-state verification, and pull-request open/detect/report) uses one deterministic selection. First the remote is selected, then its default branch is resolved from that remote's HEAD:

1. **Remote selection** — enumerate remotes (`git remote`). If there are none, the remote path is skipped everywhere (push and PR steps warn and skip). Otherwise select the remote whose HEAD symbolic ref resolves: for each remote `r` in listing order, `git symbolic-ref refs/remotes/<r>/HEAD`; the first that resolves wins. If none resolves: use `origin` when it exists; else when exactly one remote exists use it; else stop and ask the user.
2. **Default branch** — resolve FRESHLY from the remote for both the initial archive and every resume: `git ls-remote --symref <remote> HEAD`, parsing the `ref: refs/heads/<branch> HEAD` record (not the shortened ref name) and stripping the `refs/heads/` prefix to obtain the branch name. If the remote's HEAD is unresolvable, fall back to the first existing local branch of `master`, then `main`. If none resolves: stop and ask the user to name the target branch. The stale local `refs/remotes/<remote>/HEAD` is never used as the source of truth.

Push targets every effective push endpoint; remote-state checks (branch presence, tip freshness) run against EVERY pinned effective push endpoint — never against the fetch endpoint alone, so a fork-style configuration with a push URL verifies the head repository the branch was actually pushed to. The pull request is opened, detected, and reported against the base and head repositories derived below. In this repository the selection yields `origin` and `master`, and fetch and push endpoints coincide.

**Opaque endpoints.** Endpoints that cannot be parsed into a canonical identity (e.g. `file://` URLs or local paths) disable PR automation for that run: the push still happens, the flow warns and follows the manual-follow-up path, and such endpoints are pinned by a stable, non-secret fingerprint — the SHA-256 of the endpoint string with only leading/trailing ASCII whitespace trimmed (interior whitespace is significant: `/srv/repo a` and `/srv/repoa` are different strings and different fingerprints), recorded instead of the raw string. Equality between retries is judged by fingerprint; a changed fingerprint stops and asks the user.

**User-authorized repin.** Pins are immutable during normal retries, but a user who resolves a configuration problem (e.g. removing a duplicate push endpoint or publishing the branch on the base host) can authorize a repin: when a resume detects a pin mismatch, it stops and offers the user the choice to (a) keep the old pins, (b) accept the current configuration as the new pins, or (c) abort. Only user-authorized repins replace recorded pins; retries otherwise revalidate against the original pins.

**Durable pin state.** Pins and the archive destination are persisted in a durable state file at `<mainRepository>/.git/openspec-postops/<name>.json` — inside `.git`, never committed, git-scoped, and present regardless of later interruption. The file is written atomically (write-temp-then-rename) BEFORE the first remote-touching operation, updated the same way when a repin is authorized (before any remote operation resumes), and deleted after successful post-ops. The resume command carries the same pins as a fallback, but the state file is authoritative; if the two disagree, the state file wins and the discrepancy is reported.

**Repository identity for push and PR.** The pins recorded by the archive (and carried in the resume command) are:
- the selected remote name (or the explicit "no remote" state when no remote exists — a resume then revalidates that no remote has appeared, and stops/asks if one has);
- the effective push endpoint list — `git remote get-url --push --all <remote>` (all push URLs, since `git push` targets every configured push URL); when no push URL is configured this is the single fetch URL;
- the base repository identity — the CANONICAL identity of the fetch endpoint (see below), since the PR base repository is derived from it;
- the resolved base branch name (freshly resolved as above).

All endpoints are reduced to their canonical repository identity BEFORE recording, comparing, or appearing anywhere (pins, reports, logs, shell history). The canonical identity is `<lowercase-host>[:port]/<path-segments>`, extracted deterministically: for `https://`, `ssh://`, or `git://` URLs, parse the netloc as `[user[:pass]@]host[:port]` — hostname = everything after the last `@` (userinfo never) and before any `:port`, lowercased; the port, when explicitly present in the URL, is kept in the identity (different ports can reach different servers — `host:2222/group/repo` and `host:2223/group/repo` are distinct identities); path = everything after the first `/`, with a trailing `.git` stripped (multi-segment namespaces such as `group/subgroup/repo` are preserved as-is); any query string or fragment is dropped. For SCP-style `[user@]host:path[.git]` URLs, host = the substring after the last `@` (e.g. `git@host` → `host`) and before the first `:`, lowercased (SCP-style URLs carry no explicit port); path = the substring after that first colon with a trailing `.git` stripped. Equivalent endpoints expressed in different schemes map to the same canonical identity, so pins are scheme-agnostic. Canonical parsing is attempted for every endpoint; endpoints that fail become opaque fingerprints (above). A resume revalidates each pin before any remote-touching step: the remote name still exists; the canonical identities (or fingerprints) of its current effective push endpoints still match the recorded list (retargeted or added/removed destinations stop and ask the user); the canonical identity of the fetch endpoint still matches the recorded base identity; and a FRESH default-branch resolution matches the recorded base (a changed default — e.g. `master` → `main` while `master` still exists — stops and asks the user). Any mismatch stops and asks the user, so retries push, deduplicate, and open against the same repositories and base branch.

**Base and head repository derivation.** The PR's base repository is the repository hosting the default branch, derived from the fetch endpoint; the PR's head repository is the repository hosting the effective push endpoint(s). When they differ (fork-style configuration with a push URL) but share a host, the PR head ref is owner-qualified and deduplication matches the head branch within the head repository and the base branch within the base repository. When the effective push endpoint list contains multiple DISTINCT canonical identities, STOP and retain the worktree (the push destination is ambiguous; the user must resolve the configuration, after which the post-ops re-runs). When the head repository's host differs from the base repository's host, cross-forge pull requests cannot exist and the branch lives only on the other host: STOP, report, and RETAIN the worktree pending user resolution (the user publishes the branch to the base host or changes the configuration; the post-ops re-runs afterward).

Rationale: one selection algorithm avoids hardcoding `master` or `origin` into canonical skills while matching this repo today, and pins the handoff to a single repository so resumability checks inspect the same remote the push targets. Alternative rejected: hardcoding `master`/`origin` — breaks the same skills in `main`-based or multi-remote repos.

### D6: Post-archive git handoff (the post-ops)

Run after the change directory has been moved into `openspec/changes/archive/YYYY-MM-DD-<name>/` (inside the worktree). The post-ops is **resumable**: a re-run determines its starting point from the repository state instead of requiring a fixed start. Steps, in order, skipping any step whose precondition is already satisfied:

0. **Preflight**: refuse to proceed (stop and report) while any git operation is in progress — an active merge, rebase, cherry-pick, or revert (detected via `MERGE_HEAD`, `rebase-merge`/`rebase-apply`, `CHERRY_PICK_HEAD`, or `REVERT_HEAD` state, or unmerged paths in `git status`). Because git-operation state is checkout-specific, the preflight runs in the main checkout (where `git worktree` commands execute) always, and additionally in the change worktree only when that worktree still exists (a removed worktree has no state to check); an in-progress operation in either stops the flow. The post-ops performs no local merges, so there is no managed-merge exception. This applies to every git step across all phases, so a `git commit` can never accidentally complete a pre-existing operation with a change's commit message.
1. **Locate state**: if the worktree `.worktrees/<name>/` exists, revalidate it as a registered git worktree on exactly branch `change/<name>` (same check as D3 step 2; a stale directory or wrong-branch worktree stops the flow), then run steps 2–5 (it still exists after a commit/push failure — nothing is lost). If it does not exist, the worktree was already removed: verify remote state against EVERY pinned effective push endpoint (D5) and apply the pull-request status semantics of step 4 — if a matching pull request exists that is OPEN or MERGED, the handoff already finished (report its URL and status; a merged PR counts as done even when its remote branch was auto-deleted after merge, and in that case branch presence on the endpoints is waived for that endpoint); if a matching closed-unmerged pull request exists, warn and ask the user whether to reopen it; if the branch `change/<name>` exists at the pushed tip on EVERY pinned endpoint but no matching pull request exists, open the pull request now (forge-side, no worktree needed) and report. If the branch is missing or stale on any pinned endpoint and no open/merged matching pull request exists, stop and report the anomaly (an interrupted archive: the branch is not fully pushed or was never pushed).
2. **Commit remaining work** (inside the worktree): inspect `git status --porcelain`. Attributable paths — the only ones staged without asking: both sides of the archive move — `openspec/changes/<name>/` (the moved-away source, whose tracked files show as deletions) and `openspec/changes/archive/YYYY-MM-DD-<name>/` (the moved destination) — plus every path explicitly listed in the change's own artifacts: the `openspec/specs/<capability>/spec.md` files matching the delta capabilities in the change's `specs/` directory, and the concrete file paths named in the change's `tasks.md` (e.g. `README.md`, `AGENTS.md`, specific skill files). Attribution is **per path**, not per directory: any other dirty path triggers the out-of-scope prompt. Git cannot attribute individual hunks within a path to a change, so unrelated content inside an attributable file is not mechanically detectable; the mitigations are the worktree isolation (D3 — no other change can have work in this checkout), the post-ops report listing every staged path for human review, and the commit message naming the change. Task-listed paths are validated before staging (`git ls-files --error-unmatch` for tracked paths, existence for untracked ones); paths that do not exist are skipped and reported. Stage both sides of the move together in one operation so the source deletions and destination additions are staged as a rename, conditional on the source still being tracked: if `git ls-files` reports files under `openspec/changes/<name>/`, run `git add -A <source> <destination>`; otherwise run `git add -A <destination>` only (re-run-safe). If the working tree is clean, skip the commit. If dirty files exist outside the attributable paths, stop and ask the user, offering three continuations: (a) approve — the out-of-scope paths are added to this run's attributable set, staged, committed, and listed as user-approved in the report; (b) decline — stop the post-ops and report (the archive itself is already complete); (c) exclude — the user commits or stashes the out-of-scope work manually, then the post-ops re-runs with a clean attributable scope. Commit with `chore(openspec): archive change <name>` (all commits include a body explaining why, per AGENTS.md).
3. **Push**: push `change/<name>` to every effective push endpoint (D5), then verify the branch exists at the pushed tip on EVERY pinned endpoint; a verification failure stops the flow (before the pull-request step and removal). If no remote is configured, skip the push, the pull-request step, and the worktree removal with a warning, and report the local state (the worktree stays for the user to handle).
4. **Open the pull request** (forge-side, does not need the worktree): create the pull request `change/<name>` → base branch (D5) via the forge's pull-request tool (generic, harness-neutral wording per `docs/harness-mapping.md`), in the base and head repositories derived per D5. Match tuple for deduplication: head branch `change/<name>` in the head repository, base branch = the resolved default branch in the base repository. An open matching pull request → report its URL, no duplicate is created, and the flow continues to step 5. A merged matching pull request → report it as merged and continue to step 5 (handoff complete, worktree still cleaned up). A closed-unmerged matching pull request → warn, report it, and ask the user whether to reopen it or create a new one; if the user declines both options, stop the post-ops and report (the worktree is retained, nothing is lost); after the user's choice the flow continues to step 5. If the forge is unreachable or not pull-request-capable, warn, report the pushed branch (name + URL if derivable), tell the user to open the pull request manually, and continue to step 5.
5. **Remove the worktree** (from the main checkout, as the final cleanup step): `git worktree remove <path>`; it refuses on a dirty tree. At this point every handoff step has run: the work is committed, the branch is pushed, and the pull request is created or its state resolved (found existing, reported merged, or explicitly handed off for manual follow-up when the forge is unreachable); the only case that stops before removal is a closed-unmerged PR whose user declined both reopen and recreate (step 4). Removal failure is therefore non-blocking: if the worktree is dirty, warn, report that the handoff is complete, and leave the worktree for the user to clean up or for a later re-run. Removal is safe because the branch is already pushed; the local and remote branch refs remain.

Explicit outcome contract — each failure point stops, warns, or no-ops as follows. All git operations run only after the archive itself has completed, so a post-ops failure never undoes the archive:

| Condition | Outcome | Repo state |
|---|---|---|
| Not a git repo / convention inactive (D2) | Warn, skip all git steps | unchanged, archive done |
| No worktree + open/merged matching PR exists (step 1) | Report PR URL + status, done (merged PR waives branch presence) | handoff already finished |
| No worktree + branch at pushed tip on every endpoint, no matching PR (step 1) | Open the PR now, report | handoff completed |
| No worktree + branch missing/stale on any endpoint, no open/merged PR (step 1) | Stop, report the anomaly | interrupted archive, branch not fully pushed |
| Active git operation in progress in main checkout OR change worktree (step 0 preflight) | Stop, report; never run git steps into an in-progress operation | repo state untouched |
| Step 2 out-of-scope dirty files: user approves | Continue — out-of-scope paths staged, listed as user-approved | all staged work committed and pushed |
| Step 2 out-of-scope dirty files: user declines / excludes | Stop post-ops, report (decline) or user cleans up manually then re-runs (exclude) | worktree intact, work uncommitted |
| Commit (step 2) fails | Stop, report | nothing committed, worktree intact |
| Push (step 3) fails | Stop, report; nothing is lost, a re-run retries the push | worktree intact with committed work |
| No remote configured (steps 3–5) | Warn; skip push, PR, and removal, report local state | worktree kept for manual handling |
| Matching PR open (step 4) | Report its URL, no duplicate, continue to step 5 | worktree removed last |
| Matching PR merged (step 4) | Report merged, continue to step 5 | handoff complete, worktree removed |
| Matching PR closed-unmerged (step 4), user reopens or recreates | Warn, report, act on the user's choice, continue to step 5 | branch pushed, PR state resolved |
| Matching PR closed-unmerged (step 4), user declines both options | Stop post-ops, report; do NOT remove the worktree | worktree retained, nothing lost |
| Forge unreachable / not PR-capable (step 4) | Warn, report the pushed branch, tell the user to open the pull request manually, continue to step 5 | branch pushed, PR left for manual follow-up, worktree removed |
| Multiple distinct push identities (D5) | Stop, report, retain the worktree; user fixes the configuration, then re-runs and authorizes a repin when offered | worktree retained, nothing lost |
| Cross-host head/base (D5) | Stop, report, retain the worktree; user publishes the branch on the base host (or reconfigures), then re-runs and authorizes a repin when offered | worktree retained, nothing lost |
| Push tip verification fails on any pinned endpoint (step 3) | Stop, report; re-run after the endpoint recovers | worktree intact with committed work |
| Pin mismatch on resume; user authorizes repin | Accept current configuration as new pins, continue | pins replaced, retry proceeds |
| Unparseable endpoint (e.g. file:// or local path) | Warn, disable PR automation, follow the manual-follow-up path, continue to step 5 | branch pushed, PR left for manual follow-up |
| Worktree dirty at removal (step 5) | Warn (non-blocking): handoff already complete, leave worktree for user cleanup or later re-run | handoff complete, worktree retained |

Rationale: push-then-PR-then-remove ordering means the change's commits are safe on the remote and the pull request's state is resolved (created, found, or explicitly handed off for manual follow-up) before the worktree is removed, and the pull request makes merging a human decision. There are no destructive steps on the branch refs, so a failure never loses work; the worst case is a re-run. Alternatives rejected: archive-time merge/delete (superseded by the user's choice of push-and-PR), auto-merging the pull request (review must remain a human decision), and keeping the worktree after archive (the user chose worktree-removal as part of the post-ops; the branch refs survive the removal).

### D7: Remote handling

Change branches are local-only during the change's lifetime (in the worktree). At archive time the branch is pushed once and a pull request against the default branch is opened, then the worktree is removed. The branch (local and remote) is kept until the pull request merges; deletion after merge is left to the user or the forge and is never automated by the archive flow.

Rationale: pushing only at archive time keeps the remote free of half-finished per-change branches, while the pull request preserves the change for review and merges it as a human decision. Alternative rejected: pushing every change branch at propose — adds remote noise without a consumer, since review happens via the pull request at archive time.

### D8: Skill neutrality

All git steps in the skills use generic wording ("the git tool", "the default branch", "the forge's pull-request tool", "worktree") and are conditional on D2/D3. No step fails the whole workflow when the convention does not apply. This change SHALL add a "pull-request tool" mapping row to `docs/harness-mapping.md` (forge → pull-request tool names) so implementations can open, detect, and report existing pull requests consistently across harnesses.

Rationale: canonical skills are distributed to other repositories and standalone OpenSpec stores (see `docs/harness-mapping.md`); forcing `master`-centric or forge-specific assumptions there would break them. Alternative rejected: hard-failing outside the convention — hostile to other users of the skills.

## Risks / Trade-offs

- [Pull request never merged] → The post-ops report explicitly prompts the user to review and merge; the change remains archived locally regardless of merge state; the branch lingers until merge (deletion is a cheap manual step or the forge's auto-delete-on-merge).
- [Stale worktrees after interrupted runs] → Post-ops resumability keeps the worktree until push succeeds; `.worktrees/` is gitignored so stale worktrees never pollute the repo; a `git worktree prune`-style note in the report helps the user clean up.
- [Unrelated dirty files swept into the archive commit] → Worktree isolation (D3) means only this change's checkout can be dirty; pre-commit status inspection (D6.2) with a user prompt still guards within the worktree.
- [Push failure] → Stop before removing the worktree; nothing is lost, a re-run retries the push.
- [Forge unavailable at archive time] → The branch is already pushed; the report points the user to open the pull request manually.
- [Agent commits change work in the main checkout by mistake] → apply/sync ensure-worktree stops/asks (D3/D4) and the AGENTS.md documentation reduces the chance; the worktree's branch push still carries the work to the PR.
- [Skill complexity grows with guards] → Guards are small conditional checks behind one shared procedure (D3); the trade-off of safe behavior in foreign environments outweighs it.

## Migration Plan

1. **Bootstrap this change**: create the worktree with `git worktree add -b change/branch-per-change .worktrees/branch-per-change master` from the main checkout, move the proposal artifacts from the main checkout into `.worktrees/branch-per-change/openspec/changes/branch-per-change/`, stage and commit **only** that directory with `chore(openspec): propose change <name>`. Any unrelated dirty files in the main checkout (e.g. the currently modified archived story-seed file) stay there untouched — worktree isolation makes them a non-issue.
2. **First archive under the new flow**: the archive skill runs the post-ops for `branch-per-change` itself — committing, pushing `change/branch-per-change`, opening its pull request, and removing the worktree — proving the flow end-to-end; the docs and skills changed by this change reach the default branch through that pull request's merge.
3. **Existing archived changes**: nothing to migrate — they are already in the default branch's history.
4. **Rollback**: if the strategy proves burdensome, revert the docs section and the skill edits in one pull request; existing change worktrees can be removed and branches merged manually one by one. There is no data migration to undo.

## Open Questions
